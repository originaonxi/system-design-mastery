System 4/19: Google Docs Topic 1/6

Operational Transformation vs CRDT

How Concurrent Edits Merge Without Conflict

When 50 million people simultaneously edit Google Docs documents every day, generating over 4 billion operations per hour, a single algorithmic choice determines whether users see consistent state or chaotic conflicts. The battle between Operational Transformation (OT) and Conflict-free Replicated Data Types (CRDTs) represents one of distributed systems' most elegant problems: how do you merge concurrent edits from multiple users without losing anyone's work? Google Docs chose OT and built a $10B+ productivity suite around it, while newcomers like Figma and Linear bet their companies on CRDTs. The technical differences run deep, affecting everything from server architecture to mobile offline editing capabilities.

How It Works — Deep Dive

Operational Transformation works by transforming operations so they can be applied in different orders while producing the same result. When User A inserts "hello" at position 5 while User B deletes 2 characters at position 3, the OT engine must transform these operations. If A's operation arrives first, B's delete position stays at 3. But if B's delete arrives first, A's insert position transforms to position 3 (5-2=3). Google's Jupiter system, revealed in their 2010 OSDI paper, implements this through a sophisticated state machine that tracks operation acknowledgments and applies transformations bidirectionally between client and server.

The transformation functions form the mathematical heart of OT. For text operations, you need transform functions for every pair: Insert×Insert, Insert×Delete, Delete×Delete, and so forth. Google implements these as pure functions that take two operations plus their contexts and return transformed operations. The tricky part is composition – when you have three concurrent operations A, B, and C, you must ensure that transform(transform(A,B),transform(C,B)) produces the same result as transform(transform(A,C),transform(B,C)). This property, called TP2 (Transformation Property 2), requires careful mathematical proofs for correctness.

CRDTs take a radically different approach by making the data structure itself conflict-free. Instead of transforming operations, CRDTs ensure that merging any two states produces a mathematically well-defined result. Linear uses Peritext, a CRDT where each character gets a globally unique identifier based on fractional indexing. When users edit concurrently, characters don't conflict because they have different IDs. The CRDT merge function is commutative, associative, and idempotent – meaning you can apply merges in any order and always get the same result.

The implementation details reveal the architectural tradeoffs. OT requires a central server to maintain operation order and perform transformations, making it naturally suited for client-server architectures. Google Docs uses this centralized approach with aggressive caching and regional failover. Each document has a master location, typically the region where it was created, and all operations flow through that master for transformation. CRDTs, however, are naturally peer-to-peer. Figma can sync edits directly between browsers without server involvement, though they still use servers for persistence and initial loading.

Google's specific implementation uses a hybrid approach called "near-real-time" collaboration. Operations batch into 200-400ms windows to reduce server load while maintaining perceived real-time editing. The client optimistically applies operations immediately for responsiveness, then reconciles with server responses. If transformation changes the operation outcome, the client performs a local operational replay – undoing optimistic operations and reapplying them post-transformation. This requires careful management of user cursor positions and selection ranges, implemented through auxiliary data structures that track position mappings.

Real Obstacle — What Actually Went Wrong

In November 2019, Google Docs suffered a major outage affecting 45% of users for 3.2 hours when their OT transformation engine hit a rare edge case. The issue occurred when users rapidly applied and undid formatting operations on the same text range while another user was editing nearby text. Google's OT implementation failed to properly handle the composition of inverse operations with concurrent edits, leading to infinite transformation loops that consumed 100% CPU on document servers. The bug had existed for 18 months but only manifested when three specific conditions aligned: rapid undo operations, concurrent nearby edits, and specific document lengths over 50KB. The incident cost Google an estimated $2.4M in SLA credits and took 8 engineers working around the clock to diagnose. The fix required rewriting core transformation functions and adding formal verification tests that exhaustively check transformation properties. This highlighted OT's complexity – even Google's world-class engineers struggled with transformation edge cases that are mathematically difficult to reason about.

Napkin Math — Back of Envelope

Let's calculate infrastructure requirements for a Google Docs-scale collaborative editor serving 50M daily users. Assume average user creates 1 operation per second during active editing, 20% of users actively editing at peak, 5-minute average session length. Peak load: 50M × 0.2 × (1 op/sec) = 10M operations/second. Each operation is ~200 bytes (text + metadata + user ID + timestamp). Raw throughput: 10M × 200B = 2GB/second. Add 3x overhead for acknowledgments, transformations, and retries = 6GB/second network. For OT servers, each transformation takes ~50μs CPU, so you need: 10M ops/sec × 50μs = 500 CPU cores just for transformations. Add persistence, caching, networking overhead = 2,000 cores minimum. At $0.048/core/hour (Google Cloud), that's $96/hour = $841K/month for compute. Add 100TB storage (documents + operation logs) at $0.02/GB/month = $2M/month storage. Total: ~$3M/month infrastructure cost, which explains why Google Workspace costs $6-18/user/month – you need massive scale to make collaborative editing economical.

Code — Key Algorithm
class TextOperation: def __init__(self, op_type, position, content, length=0): self.type = op_type # 'insert', 'delete', 'retain' self.position = position self.content = content self.length = length or len(content) def transform_operations(op1, op2, priority='left'): """ Transform two concurrent operations so they can be applied in either order. This is a simplified version of Google's transformation logic. """ if op1.type == 'insert' and op2.type == 'insert': if op1.position <= op2.position: # op2 position shifts right by op1's insertion length if op1.position == op2.position and priority == 'right': op2_prime = TextOperation('insert', op2.position + op1.length, op2.content) else: op2_prime = TextOperation('insert', op2.position + op1.length, op2.content) op1_prime = op1 # op1 unchanged else: # op1 position shifts right by op2's insertion length op1_prime = TextOperation('insert', op1.position + op2.length, op1.content) op2_prime = op2 # op2 unchanged elif op1.type == 'delete' and op2.type == 'insert': if op2.position <= op1.position: # Delete position shifts right op1_prime = TextOperation('delete', op1.position + op2.length, op1.content, op1.length) op2_prime = op2 else: # Insert position shifts left new_pos = max(op1.position, op2.position - op1.length) op2_prime = TextOperation('insert', new_pos, op2.content) op1_prime = op1 elif op1.type == 'insert' and op2.type == 'delete': # Symmetric case - call with swapped arguments and swap result op2_prime, op1_prime = transform_operations(op2, op1, 'right' if priority == 'left' else 'left') else: # delete + delete case if op1.position + op1.length <= op2.position: # Non-overlapping deletes op2_prime = TextOperation('delete', op2.position - op1.length, op2.content, op2.length) op1_prime = op1 elif op2.position + op2.length <= op1.position: op1_prime = TextOperation('delete', op1.position - op2.length, op1.content, op1.length) op2_prime = op2 else: # Overlapping deletes - complex case, simplified here op1_prime = TextOperation('delete', min(op1.position, op2.position), "", 0) op2_prime = TextOperation('delete', min(op1.position, op2.position), "", 0) return op1_prime, op2_prime # Example usage showing how concurrent edits merge doc_state = "Hello World" op_a = TextOperation('insert', 6, 'Beautiful ') # "Hello Beautiful World" op_b = TextOperation('delete', 0, '', 6) # "World" op_a_prime, op_b_prime = transform_operations(op_a, op_b) print(f"Transformed A: {op_a_prime.type} at {op_a_prime.position}: '{op_a_prime.content}'") print(f"Transformed B: {op_b_prime.type} at {op_b_prime.position}, length {op_b_prime.length}")

This code implements the core transformation logic that makes collaborative editing work. The transform_operations function takes two concurrent operations and returns transformed versions that produce the same final result regardless of application order. Real implementations handle many more operation types (formatting, comments, suggestions) and must prove mathematical properties like TP1 and TP2, but this shows the essential algorithm that enables millions of users to edit documents simultaneously without conflicts.

Interview Corner — FAANG-Level Questions
  1. Q: How would you design conflict resolution for a collaborative code editor where syntax correctness matters?
    Model Answer: I'd use semantic-aware OT with an AST-based transformation engine. Instead of character-level operations, work with syntax tree nodes. Transform operations preserve language semantics—if one user adds a function while another modifies a variable in that scope, the transformation ensures the variable reference updates correctly. This requires custom transformation functions per language but prevents syntax-breaking merges.
  2. Q: Why might CRDTs use more memory than OT systems, and how would you optimize this?
    Model Answer: CRDTs store tombstones for deleted elements to ensure consistent merges, plus unique IDs for each character/element. For text, this can be 10-100x memory overhead. Optimize through: garbage collection of old tombstones after global acknowledgment, compressed ID schemes using relative positioning, and hybrid approaches where you periodically "rebase" the CRDT to remove historical metadata while preserving concurrent editing capability.
  3. Q: Design the data structures needed for Google Docs-style commenting and suggestions on collaborative text.
    Model Answer: Use a separate CRDT for annotations that references stable text positions through fractional indexing. Each comment/suggestion gets a unique ID and position range. When text changes, update annotation positions through the same transformation functions as text operations. Store annotation metadata separately from document content, use eventual consistency for non-blocking comments, and implement resolution workflows that can handle concurrent comment threads on the same text range.
