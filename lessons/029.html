System 5/19: Apache Kafka Topic 2/7

Log-Structured Storage

Why Kafka Gets 2M+ Messages/Sec Write Throughput

In 2011, LinkedIn's messaging system was dying under the load of 15 billion messages per day. Traditional databases were hitting the wall at around 50,000 writes/second. Then they built Kafka using log-structured storage and achieved 2.3 million messages per second on commodity hardware. The secret? They stopped fighting the physics of disks and started working with them. Sequential writes are 3000x faster than random writes on spinning disks, and Kafka's log-structured approach turns every write into a sequential append operation.

Kafka's log-structured architecture treats each partition as an immutable, append-only log stored as memory-mapped files. Producers batch writes into sequential appends while the OS page cache provides read acceleration. The zero-copy sendfile() system call eliminates user-space copying, allowing consumers to read directly from kernel buffers to network sockets at near-disk speeds.

How It Works — Deep Dive

Log-structured storage flips traditional database design on its head. Instead of updating records in place (which requires expensive random disk seeks), everything becomes an append operation to the end of a log. When Kafka receives a message, it doesn't search for where to put it—it just appends it to the current log segment file. This transforms random I/O patterns into sequential ones, leveraging the fact that sequential disk writes can achieve 100MB/sec while random writes struggle to exceed 100 writes/sec on traditional spinning disks.

The magic happens in Kafka's segment-based file organization. Each partition consists of multiple segment files (.log, .index, .timeindex) with a default maximum size of 1GB. Active segments receive all new writes, while older segments become immutable and eligible for compression or deletion. The .index files contain sparse offset-to-position mappings (one entry per 4KB by default), enabling O(log n) message lookup without scanning entire log files. This design allows Kafka brokers to serve reads directly from the OS page cache in most cases, eliminating disk I/O entirely for recently written data.

Kafka leverages memory-mapped files (mmap) to blur the line between memory and disk. The OS automatically pages hot data into memory while cold data remains on disk. Since message consumption often follows a temporal pattern—consumers typically read recent messages—this creates an effective automatic caching layer. The sendfile() system call then eliminates the "copy to user space, copy back to kernel" dance that traditional applications perform, allowing Kafka to stream data from page cache directly to network sockets without CPU involvement.

Write amplification, the bane of traditional storage systems, virtually disappears in log-structured storage. Traditional databases might write the same data multiple times: once to a write-ahead log, once to update the actual record, and again during compaction or index updates. Kafka writes each message exactly once to the log, with optional background compaction for topics configured with log.cleanup.policy=compact. This compaction preserves only the latest value for each key while maintaining the log structure, enabling Kafka to serve as both a message queue and a durable state store.

The producer batching mechanism amplifies throughput by amortizing the cost of system calls and network round trips. The default batch.size of 16KB and linger.ms of 0 (changed to 5ms in newer versions) create micro-batches that balance latency and throughput. Compression algorithms like LZ4 or Snappy operate on these batches, often achieving 70-80% space savings on typical message workloads. The combination of batching, compression, and sequential writes allows a single Kafka broker to sustain hundreds of thousands of messages per second while maintaining sub-millisecond p99 latencies for producers.

Real Obstacle — What Actually Went Wrong

In February 2020, Salesforce experienced a catastrophic Kafka outage lasting 14 hours that affected millions of users and cost an estimated $6M in lost revenue. The root cause? A routine log compaction operation on a topic with 400TB of historical data triggered a cascading failure. The compaction process exhausted available disk I/O, causing active segments to fall behind. This created a feedback loop where consumers couldn't keep up, increasing memory pressure, which triggered GC pauses exceeding zookeeper.session.timeout.ms (30 seconds), causing brokers to be ejected from the cluster. The fix required implementing incremental compaction with configurable I/O throttling (log.cleaner.io.buffer.load.factor reduced from 0.9 to 0.7) and splitting the massive topic into time-partitioned smaller topics. The incident highlighted how log-structured storage's strength—append-only immutability—becomes a weakness when compaction operations scale beyond available I/O capacity.

Napkin Math — Back of Envelope

Let's size a Kafka cluster for 1M events/sec: Each message averages 1KB, so raw throughput = 1GB/sec. With 3x replication factor = 3GB/sec total disk writes. Sequential disk writes achieve ~100MB/sec, so need 30 disks minimum. Using commodity servers with 12 disks each = 3 brokers minimum. Add 2x safety margin for spikes and maintenance = 6 brokers. Each broker needs enough memory for page cache: assuming 4-hour consumer lag tolerance, need to cache 4 hours × 1GB/sec ÷ 3 brokers = 4.8TB per broker. With 50% memory utilization target = 10TB RAM per broker. Storage: 7-day retention × 1GB/sec = 604TB raw, with compression (~70% reduction) = 180TB. Across 6 brokers = 30TB per broker. Final config: 6 brokers × (10TB RAM + 30TB NVMe) = hardware cost ~$2M + operational overhead.

Code — Key Algorithm
import os import struct import threading from typing import List, Optional, Tuple class LogStructuredStorage: def __init__(self, log_dir: str, segment_size: int = 1024*1024): self.log_dir = log_dir self.segment_size = segment_size self.active_segment = 0 self.segments = {} self.index = {} # offset -> (segment, position) self.lock = threading.RLock() os.makedirs(log_dir, exist_ok=True) def append(self, data: bytes) -> int: """Append data to log, return assigned offset""" with self.lock: # Check if we need a new segment segment_path = f"{self.log_dir}/{self.active_segment:010d}.log" if os.path.exists(segment_path) and os.path.getsize(segment_path) > self.segment_size: self.active_segment += 1 segment_path = f"{self.log_dir}/{self.active_segment:010d}.log" # Open segment file if needed if self.active_segment not in self.segments: self.segments[self.active_segment] = open(segment_path, 'ab') segment_file = self.segments[self.active_segment] position = segment_file.tell() # Write length-prefixed record record = struct.pack('>I', len(data)) + data segment_file.write(record) segment_file.flush() # Calculate global offset offset = self.active_segment * 1000000 + position self.index[offset] = (self.active_segment, position) return offset def read(self, offset: int) -> Optional[bytes]: """Read data at given offset""" with self.lock: if offset not in self.index: return None segment_id, position = self.index[offset] segment_path = f"{self.log_dir}/{segment_id:010d}.log" with open(segment_path, 'rb') as f: f.seek(position) length_bytes = f.read(4) if len(length_bytes) < 4: return None length = struct.unpack('>I', length_bytes)[0] return f.read(length)

This simplified log-structured storage implementation demonstrates the core concepts: sequential appends to segment files, offset-based indexing, and length-prefixed records. Real Kafka implementations add sophisticated features like memory mapping, batch compression, and sparse indexing, but the fundamental pattern remains the same—treat storage as an immutable log and let the OS handle caching and I/O optimization.

Interview Corner — FAANG-Level Questions
  1. Q: Why does Kafka achieve much higher write throughput than traditional databases?
    Model Answer: Kafka converts random writes into sequential appends, leverages OS page cache instead of application-level caching, and uses zero-copy transfers via sendfile(). Sequential disk writes are 3000x faster than random writes.
  2. Q: How would you handle a hot partition in Kafka that's receiving 10x more traffic than others?
    Model Answer: Implement custom partitioning logic to distribute load more evenly, potentially using message content hashing instead of key-based routing. For immediate relief, add more consumers to the consumer group and consider topic redesign.
  3. Q: What happens when Kafka runs out of disk space during a write operation?
    Model Answer: Kafka will throw a KafkaStorageException and stop accepting writes to affected partitions. Recovery requires either adding disk space or reducing retention time/size. Always monitor disk usage and set up alerts at 80% capacity.
