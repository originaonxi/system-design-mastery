System 1/19: Stock Exchange Topic 3/7

Market Data Feed Architecture

Distributing Real-Time Prices to Millions of Traders Worldwide

Every trading day, US stock exchanges generate over 50 billion market data messages—quotes, trades, and order book updates flowing at peak rates exceeding 10 million messages per second. Behind every split-second trading decision lies a marvel of distributed systems engineering: the market data feed architecture that delivers price information to millions of traders worldwide with sub-millisecond latency. When this system fails, as it did during NASDAQ's 3-hour trading halt in August 2013, billions of dollars in trading volume vanishes and market confidence evaporates.

How It Works — Deep Dive

Market data feeds operate on a publish-subscribe architecture where each of the 13 major US equity exchanges publishes their order book changes, trades, and quotes to centralized Securities Information Processors. The SIP system, managed by the Consolidated Tape Association (CTA) and Unlisted Trading Privileges (UTP), normalizes this heterogeneous data into three primary consolidated feeds: CTA-A (NYSE-listed securities), CTA-B (regional exchange trades), and UTP (NASDAQ-listed securities).

The technical heart of the system lies in its message sequencing and gap detection mechanisms. Each message carries a strictly monotonic sequence number, critical for maintaining data integrity across unreliable network transport. When the SIP receives a trade from NYSE with sequence 12843756 followed by sequence 12843758, it immediately detects the gap and requests retransmission of message 12843757. This happens millions of times per day—network packets drop, switches fail, and fiber cables get cut by construction crews.

Transport protocol selection reveals sophisticated engineering tradeoffs. High-frequency trading firms receive direct market data via UDP multicast on dedicated 10-40 Gigabit fiber connections, accepting potential packet loss in exchange for minimal latency overhead. Retail brokers typically consume normalized feeds via TCP or WebSocket connections, prioritizing reliability over the last few microseconds. The UDP multicast approach is particularly elegant: instead of unicasting 2GB/sec to each of 1000 subscribers (requiring 2TB/sec total bandwidth), multicast delivers the same 2GB/sec stream that all subscribers can receive simultaneously.

Data normalization presents enormous complexity when aggregating feeds from exchanges using different message formats, precision levels, and timestamp schemas. NASDAQ's ITCH protocol uses 8-byte timestamps with nanosecond precision, while NYSE's Pillar feed uses microsecond precision. The SIP must reconcile these differences, handle clock skew between exchange data centers (sometimes 10+ milliseconds apart), and maintain temporal ordering across venues. Message formats range from 40-byte equity trades to 200+ byte options quotes, with the SIP processing an average message size of approximately 200 bytes.

Fault tolerance mechanisms include multiple layers of redundancy. Primary and backup SIP processors run in active-passive configuration across geographically separated data centers in Mahwah, NJ and Chicago. Each processor maintains complete order books for all 8,000+ listed securities, requiring 50+ GB of in-memory state. When the primary fails, backup systems must seamlessly take over without losing a single message—any gap would force expensive recovery procedures involving historical data reconstruction from exchange logs.

Real Obstacle — What Actually Went Wrong

On August 22, 2013, at 12:14 PM EST, NASDAQ abruptly halted trading for all NASDAQ-listed securities, including Apple, Google, and Microsoft—representing roughly 40% of US equity trading volume. The culprit: a cascading failure in the Securities Information Processor (SIP) that couldn't keep up with an unexpected surge in quote traffic. The system processed over 20 million quotes in the seconds leading up to the halt, overwhelming the SIP's processing capacity and causing quote delays of over 20 seconds. With stale prices, market makers couldn't safely provide liquidity, forcing NASDAQ to implement a complete trading halt. The outage lasted 3 hours and 8 minutes, wiping out approximately $5 billion in trading volume and triggering SEC investigations. The root cause: insufficient capacity planning for quote message spikes and inadequate circuit breakers in the SIP architecture itself. NASDAQ ultimately paid a $10 million fine—the largest in SEC history at the time for a market outage.

Napkin Math — Back of Envelope

Start with peak load: 10M messages/sec × 200 bytes average = 2GB/sec raw throughput. For 1000 market data subscribers using unicast TCP: 1000 × 2GB/sec = 2TB/sec total bandwidth required. Switch to UDP multicast: same 2GB/sec serves all subscribers = 1000x bandwidth savings. Memory requirements: 8000 securities × 100 price levels × 50 bytes per level × 2 sides (bid/ask) = ~80MB per order book snapshot. Add message queuing: 10M msg/sec × 1 second buffer × 200 bytes = 2GB RAM for buffering. Total per SIP processor: 80MB + 2GB + overhead = ~3GB RAM minimum. For redundancy across 3 data centers: 3 × 2GB/sec × $0.10 per GB (network costs) = $600/sec = $50K/day just in bandwidth costs during market hours.

This SIP processor implementation demonstrates the core gap detection and message ordering logic. The algorithm maintains expected sequence numbers per exchange, buffers out-of-order messages, and processes them once gaps are filled. The consolidated sequence number ensures global ordering across all exchanges while preserving per-exchange message integrity.

Interview Corner — FAANG-Level Questions
  1. Q: Why does market data use UDP multicast instead of TCP?
    Model Answer: UDP multicast provides 1000x bandwidth savings (2GB/sec serves all vs 2TB/sec for individual TCP streams) and eliminates TCP's head-of-line blocking. While packets may drop, financial firms prefer handling retransmissions themselves rather than accepting TCP's variable latency during congestion.
  2. Q: How would you handle message gaps in a market data feed?
    Model Answer: Maintain per-exchange sequence counters, buffer out-of-order messages, and request retransmission for detected gaps. Implement exponential backoff for retransmission requests and circuit breakers to prevent gap storms. For critical applications, maintain redundant feed connections and cross-validate sequence integrity.
  3. Q: Design a system to normalize data from 13 different exchanges into one unified feed.
    Model Answer: Build SIP processors that map heterogeneous exchange protocols to canonical message format, handle different timestamp precisions via clock synchronization, maintain consolidated sequence numbering, and implement schema versioning for backward compatibility. Use message queuing for temporal ordering and geographic distribution for fault tolerance.
