Payment Flow Architecture

Auth → Capture → Settlement: How Stripe Processes $1T+ Annually

Every second, Stripe processes over $32,000 in payments across 46 countries, handling the three-phase dance that turns a customer's "Buy Now" click into actual money in a merchant's bank account. This isn't just moving numbers between databases—it's orchestrating a complex ballet involving banks, card networks, regulatory compliance, and fraud detection systems that must complete in under 500ms while maintaining 99.99% uptime. The difference between authorization and settlement isn't academic; it's the $847 billion gap that sits in payment limbo at any given moment across the global financial system.

This architecture separates the three critical phases of payment processing: Authorization (fraud check + fund reservation), Capture (fund movement initiation), and Settlement (actual money transfer). Each phase has different latency requirements, rollback mechanisms, and consistency guarantees. The Token Vault ensures PCI compliance by never storing raw card data, while the Ledger Database maintains double-entry bookkeeping for financial accuracy.

How It Works — Deep Dive

The payment flow begins when a customer submits payment information, but before any money moves, Stripe's fraud detection pipeline evaluates over 250 signals in real-time. This includes device fingerprinting, behavioral biometrics, velocity checks, and machine learning models trained on billions of transactions. The fraud engine uses a gradient boosting model (specifically LightGBM) running inference in under 50ms, scoring each transaction on a 0-1000 scale. Transactions scoring above 750 trigger 3D Secure authentication, while those above 900 are automatically declined.

Authorization happens through the card networks using ISO 8583 messaging protocol. Stripe maintains direct connections to Visa (VisaNet), Mastercard (Banknet), American Express, and Discover networks through certified Payment Service Provider (PSP) infrastructure. The authorization message contains a cryptographically hashed version of the card data (tokenized via EMV standards), transaction amount, merchant category code, and fraud scoring results. The issuing bank responds within 2-4 seconds with either approval (response code 00), decline, or request for additional authentication. Importantly, authorization only reserves funds—no money actually moves during this phase.

Capture occurs when the merchant is ready to fulfill the order, typically within 7 days of authorization (this window varies by card network and issuer). Stripe's Capture Engine maintains a distributed queue using Apache Kafka with exactly-once delivery semantics to prevent duplicate captures. The capture message triggers fund movement from the cardholder's account to the acquiring bank's settlement account. This process uses the card networks' clearing and settlement systems—massive batch processing operations that run multiple times daily. Visa processes over 150 million transactions daily through VisaNet, which operates on IBM Z15 mainframes with 99.9999% uptime requirements.

Settlement is the final phase where funds move from the acquiring bank to the merchant's bank account. Stripe batches settlements by merchant and currency, typically executing payouts daily via ACH (2-3 business days) or wire transfers (same day for premium accounts). The Settlement Service maintains idempotent operations using unique transaction IDs and implements two-phase commit protocols to ensure atomic money movement. For international transactions, Stripe partners with banks like Citibank and JPMorgan Chase, which maintain correspondent banking relationships globally. Currency conversion happens at settlement time using mid-market rates plus a 1% spread.

The entire system maintains ACID properties through careful state machine design. Each transaction progresses through states: Created → Authorized → Captured → Settled, with specific rollback procedures at each stage. Authorization reversals must happen within 24 hours, while captures can be refunded up to 180 days later (varying by card network). Stripe's Ledger Database implements double-entry bookkeeping with cryptographic checksums to detect any discrepancies. Every financial operation creates offsetting debit and credit entries, with the system running continuous reconciliation jobs to match internal ledgers against bank statements and card network reports.

Real Obstacle — What Actually Went Wrong

On March 15, 2019, Stripe experienced a 4-hour partial outage affecting payment processing across Europe due to a database failover incident in their Dublin data center. The root cause was a PostgreSQL primary-replica lag that exceeded 30 seconds during a routine maintenance window, triggering an automatic failover. However, the failover process revealed a race condition in their distributed lock manager (built on Redis Cluster) that caused payment authorizations to get stuck in "pending" state. Over 40,000 merchants were affected, with transaction volumes dropping by 67% during peak hours. The incident cost an estimated $15M in lost transaction fees and required manual intervention to replay 180,000 stuck transactions. Stripe's post-mortem revealed they needed better database failover testing under load and implemented "chaos engineering" practices, deliberately triggering failovers during peak traffic to validate their systems. They also redesigned their lock manager to use compare-and-swap operations instead of distributed locks for critical payment state transitions.

• Authorization latency budget: 500ms P99 → need <100ms internal processing
• Database writes: 60 TPS × 4 writes/transaction (auth, capture, ledger, audit) = 240 writes/sec
• Storage: 1M transactions × 2KB avg payload × 7 years retention = 14GB/day → 36TB total
• Memory cache: 60 TPS × 500ms × 2KB = 60MB active working set → 1GB Redis cluster
• Bandwidth: 60 TPS × 2KB × 2 (request/response) = 240KB/s → 2Mbps
• Servers needed: 60 TPS ÷ 20 TPS/server (with headroom) = 3 application servers + 2 replicas = 5 servers
Result: 5 application servers, 2-node PostgreSQL cluster, 3-node Redis cluster, 36TB storage

import time import hashlib import uuid from enum import Enum from dataclasses import dataclass from typing import Optional class TransactionState(Enum): CREATED = "created" AUTHORIZED = "authorized" CAPTURE_PENDING = "capture_pending" CAPTURED = "captured" SETTLED = "settled" FAILED = "failed" @dataclass class PaymentTransaction: id: str amount: int # Amount in cents currency: str state: TransactionState auth_code: Optional[str] = None created_at: int = None def __post_init__(self): if self.created_at is None: self.created_at = int(time.time()) class PaymentProcessor: def __init__(self): self.transactions = {} # In practice, this would be a database def create_authorization(self, amount: int, currency: str, card_token: str) -> PaymentTransaction: """ Create and authorize a payment transaction Implements the auth flow with idempotency and fraud checking """ # Generate idempotent transaction ID tx_id = str(uuid.uuid4()) # Create transaction record transaction = PaymentTransaction( id=tx_id, amount=amount, currency=currency, state=TransactionState.CREATED ) # Fraud scoring (simplified) fraud_score = self._calculate_fraud_score(amount, card_token) if fraud_score > 750: transaction.state = TransactionState.FAILED return transaction # Simulate card network authorization auth_success = self._authorize_with_network(amount, card_token) if auth_success: transaction.state = TransactionState.AUTHORIZED transaction.auth_code = self._generate_auth_code() else: transaction.state = TransactionState.FAILED self.transactions[tx_id] = transaction return transaction def capture_payment(self, tx_id: str) -> bool: """ Capture an authorized payment - triggers actual money movement """ transaction = self.transactions.get(tx_id) if not transaction or transaction.state != TransactionState.AUTHORIZED: return False # Check authorization age (typically 7 days max) if int(time.time()) - transaction.created_at > 7 * 24 * 3600: return False transaction.state = TransactionState.CAPTURE_PENDING # Simulate capture processing capture_success = self._process_capture(transaction) if capture_success: transaction.state = TransactionState.CAPTURED return True else: transaction.state = TransactionState.FAILED return False def _calculate_fraud_score(self, amount: int, card_token: str) -> int: # Simplified fraud scoring based on amount and card hash card_hash = int(hashlib.md5(card_token.encode()).hexdigest()[:8], 16) base_score = (amount // 100) + (card_hash % 500) return min(base_score, 1000) def _authorize_with_network(self, amount: int, card_token: str) -> bool: # Simulate 95% success rate for card network auth return (hash(card_token) % 100) < 95 def _generate_auth_code(self) -> str: return f"AUTH{int(time.time())}"[-8:] def _process_capture(self, transaction: PaymentTransaction) -> bool: # Simulate 99% capture success rate return (hash(transaction.id) % 100) < 99

This implementation demonstrates the core state machine for payment processing, including idempotent transaction creation, fraud scoring, and the separation between authorization and capture. The fraud scoring uses a simple hash-based approach for demonstration—production systems use sophisticated ML models with hundreds of features. Note how authorization success doesn't guarantee capture success, reflecting real-world scenarios where banks may decline captures due to insufficient funds or changed risk profiles.

Interview Corner — FAANG-Level Questions
  1. Q: How would you design the fraud detection system to minimize false positives while catching 99%+ of fraudulent transactions?
    Model Answer: Implement a multi-layered approach: real-time rule engine for known fraud patterns (<50ms), ML models for anomaly detection (gradient boosting on transaction velocity, device fingerprinting, behavioral biometrics), and human-in-the-loop for edge cases. Use A/B testing to optimize model thresholds, maintaining separate models per merchant vertical since fraud patterns differ significantly.
  2. Q: What happens if your system authorizes a payment but the capture fails 3 days later due to insufficient funds?
    Model Answer: Authorization only reserves funds temporarily—the issuing bank can remove the hold if account balance changes. We handle this with automatic retry logic (exponential backoff), merchant notifications, and fallback to partial authorization for lower amounts. Critical to maintain idempotency and proper transaction state management to prevent duplicate charges.
  3. Q: How do you ensure exactly-once processing when a merchant calls your capture API multiple times due to network timeouts?
    Model Answer: Implement idempotency using client-generated idempotency keys stored with transaction state. Each API call checks if the operation was already performed with the same key, returning the original result instead of processing again. Use database constraints and atomic compare-and-swap operations to handle race conditions between concurrent requests.
