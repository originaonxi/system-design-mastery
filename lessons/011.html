Fraud Detection ML Pipeline

Stripe Radar: Blocking 500M+ Fraudulent Attempts Per Year in Real-Time

Every 100 milliseconds, Stripe's fraud detection system makes a life-or-death decision for an online business. With $640 billion in payment volume processed annually, a single percentage point improvement in fraud detection accuracy translates to hundreds of millions in saved losses. Stripe Radar, their ML-powered fraud prevention system, processes over 1.5 billion transactions yearly while maintaining sub-100ms p99 latency and blocking 99.9% of fraudulent attempts before they complete. This system represents one of the most sophisticated real-time ML pipelines in production, combining feature engineering at massive scale, ensemble models, and adversarial learning to stay ahead of constantly evolving fraud patterns.

How It Works — Deep Dive

Stripe's fraud detection begins the moment a payment request hits their API gateway. The system extracts over 10,000 features from each transaction, ranging from obvious signals like transaction amount and merchant category to sophisticated behavioral indicators like typing cadence, mouse movement patterns, and network topology analysis. The feature extraction happens in parallel across multiple dimensions: individual user behavior (velocity of transactions, geographical patterns, device consistency), merchant risk profiles (historical chargeback rates, business type, age), and network effects (shared payment methods, IP clusters, device fingerprint similarities).

The feature store architecture uses a hybrid approach with Redis for ultra-low latency feature serving (sub-1ms lookups) and Amazon S3 for historical feature storage and batch computation. Critical features like "number of unique cards used from this IP in the last hour" are pre-computed and updated in real-time using Apache Flink streaming jobs. The system maintains approximately 500TB of feature data with automatic expiration policies and compression to manage costs. Feature freshness is crucial—staleness beyond 5 minutes can reduce model accuracy by up to 15% for certain fraud patterns.

The ML pipeline employs an ensemble of specialized models rather than a single monolithic classifier. A gradient boosting model (XGBoost) handles tabular features and accounts for 60% of the final prediction weight, while deep neural networks process sequence data like transaction histories and behavioral patterns. Graph neural networks analyze network effects, identifying fraud rings where multiple accounts share devices, payment methods, or behavioral signatures. Each model is trained on different time windows: real-time models on the last 7 days of data for rapid adaptation, and stable models on 90+ days for robust pattern recognition.

The adversarial training component continuously evolves models against sophisticated attackers. Fraudsters adapt quickly—new attack patterns can emerge and scale within hours. Stripe's system employs generative adversarial networks (GANs) to simulate potential fraud evolution and trains defensive models against these synthetic attacks. This approach, combined with active learning on uncertain predictions, allows the system to maintain 99.9%+ accuracy even as fraud patterns shift. The training pipeline processes 50+ billion feature vectors daily, with model updates deployed multiple times per day through canary releases that gradually increase traffic exposure while monitoring for accuracy degradation.

Decision making happens through a sophisticated scoring and threshold system. Rather than binary fraud/legitimate classification, the system outputs continuous risk scores from 0-100. Dynamic thresholds adjust based on merchant risk tolerance, transaction value, and current fraud attack patterns. High-value transactions (>$1000) use ensemble voting with human review queues, while micro-transactions rely on faster single-model decisions. The system also implements explanation generation using SHAP (SHapley Additive exPlanations) values, allowing merchants to understand why specific transactions were flagged and enabling rapid appeals processing.

Real Obstacle — What Actually Went Wrong

In March 2019, Stripe's fraud detection system experienced a catastrophic false positive spike that blocked 12% of legitimate transactions over a 4-hour period, costing merchants an estimated $50M in lost sales. The root cause was a model update that incorrectly weighted a behavioral feature during the European morning rush (8-11 AM CET). A machine learning engineer had deployed a new neural network model that treated rapid successive payment attempts as highly suspicious. However, the training data was biased toward US patterns and didn't account for European mobile payment behavior during commute hours, where users frequently retry failed payments due to poor cellular connectivity. The system's normal canary deployment process was bypassed due to an urgent security patch, and the monitoring alerts for false positive rates were configured with a 6-hour delay to avoid noise from daily patterns. By the time the issue was detected, major European e-commerce sites were reporting 15-20% drops in conversion rates. The fix required a full model rollback and implementing geographic stratification in training data, plus real-time false positive monitoring with 5-minute alert windows. The incident led to Stripe implementing "fraud-ops" war rooms and stricter deployment gates for models affecting high-traffic regions.

Napkin Math — Back of Envelope

Let's size the infrastructure for processing Stripe's 1.5B annual transactions. That's ~4.8M transactions/day or ~55 TPS average, ~550 TPS peak (10x). Each transaction requires 10K features, averaging 4 bytes per feature = 40KB feature data per transaction. Feature serving: 550 TPS × 40KB = 22 MB/s read throughput. With 3x replication, we need 66 MB/s. Redis can handle ~100K ops/s per node, so we need ~6 Redis nodes for reads plus 3x for availability = 18 nodes. For ML inference: assuming 50ms per prediction and 550 TPS, we need 550 × 0.05 = 27.5 concurrent predictions. With TensorFlow Serving on GPUs handling ~100 concurrent predictions per instance, we need ~1 GPU instance with 3x for availability = 3 instances. Historical storage: 1.5B transactions/year × 40KB = 60TB/year. With 5-year retention and compression (4:1 ratio), we need ~75TB total storage. Training pipeline: processing 50B feature vectors/day at 4 bytes each = 200GB/day training data. Total infrastructure: 18 Redis nodes (~$15K/month), 3 GPU instances (~$6K/month), 75TB storage (~$1.5K/month), plus networking and compute for training (~$25K/month) = ~$47.5K/month infrastructure cost.

This fraud detection implementation demonstrates key concepts: velocity-based feature extraction, device fingerprinting for identity verification, and multi-signal risk scoring. The velocity windows track user behavior patterns over time, while device fingerprinting detects account takeover attempts. In production systems like Stripe's, this basic approach scales to thousands of features with sophisticated ML models, but the core principles remain: behavioral analysis, device consistency, and real-time pattern detection.

Interview Corner — FAANG-Level Questions
  1. Q: How would you handle concept drift in a fraud detection system where attackers constantly evolve their strategies?
    Model Answer: Implement continuous learning with sliding window retraining, adversarial training using GANs to simulate attack evolution, and ensemble models with different time horizons. Use online learning algorithms for rapid adaptation and A/B test model versions to detect performance degradation before full deployment.
  2. Q: Design a feature store that serves 100K QPS with sub-5ms latency for fraud detection features.
    Model Answer: Use tiered storage: Redis for hot features (last 24h user activity), DynamoDB for warm features (30-day patterns), S3 for cold features (historical analysis). Pre-compute aggregate features in streaming pipelines, partition by user_id with consistent hashing, and implement read-through caching with TTL-based invalidation.
  3. Q: How do you balance false positives vs false negatives in fraud detection, and how does this change based on transaction value?
    Model Answer: Use dynamic thresholds based on transaction risk-reward ratios. For high-value transactions, accept higher false positive rates to minimize fraud losses. Implement cost-sensitive learning with asymmetric loss functions. Use human-in-the-loop review for uncertain predictions and continuous threshold optimization based on business metrics, not just ML accuracy.
