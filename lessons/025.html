Conflict Resolution Deep Dive

Google Uses OT, Figma Uses CRDT: Which Wins?

When Google Docs processes 2.6 billion edits per day across 2 billion documents, every millisecond of conflict resolution matters. The choice between Operational Transformation (OT) and Conflict-free Replicated Data Types (CRDTs) isn't just academic—it's the difference between Google's $280B workspace empire and Figma's $20B exit to Adobe. Both solve the same fundamental problem: how do you let millions of users edit the same document simultaneously without creating chaos? The answer reveals one of the most elegant battles in distributed systems.

How It Works — Deep Dive

Operational Transformation, first formalized in the 1989 GROVE paper by Ellis and Gibbs, solves collaborative editing through mathematical transformation functions. When User A types "hello" at position 0 while User B simultaneously deletes character 1, OT transforms these operations so they can be applied in any order while maintaining consistency. Google's implementation uses a Jupiter-style client-server model where each operation gets transformed against all concurrent operations using the transformation matrix T(op1, op2).

The Jupiter system maintains two key invariants: the CCI (Causality-preservation, Convergence, Intention-preservation) properties and a state space that ensures all replicas converge to identical states. Google's OT implementation extends this with a hybrid operational transform that handles not just text insertion and deletion, but rich formatting, comments, suggestions, and complex document structures. The server maintains a global operation sequence number and uses vector clocks to track causality relationships between operations from different clients.

CRDTs take a fundamentally different approach. Instead of transforming operations, they design data structures that are inherently conflict-free. Figma uses a variant of RGA (Replicated Growable Array) CRDTs where each character gets a unique identifier based on logical timestamps. When two users insert text at the same position, the CRDT uses deterministic ordering rules (like lexicographic comparison of site IDs) to decide the final order. This eliminates the need for a central transformation server—clients can merge states directly.

The key difference lies in network topology and consistency models. OT requires a star topology with a central server that serializes all operations and broadcasts transformations. This gives strong consistency but creates a single point of failure and requires more network round-trips. CRDTs enable a mesh topology where peers can synchronize directly, providing better partition tolerance and offline capabilities. However, CRDTs typically consume more memory due to metadata overhead and can have complex deletion semantics.

Google's specific OT implementation uses differential synchronization on top of basic OT, where clients maintain shadow copies of the document state. When network partitions occur, clients continue working on their local copy and reconcile changes when connectivity resumes. The system uses a three-way merge algorithm similar to Git, but adapted for real-time collaborative editing. This hybrid approach gives Google the strong consistency of OT with some partition tolerance benefits typically associated with CRDTs.

Real Obstacle — What Actually Went Wrong

In March 2019, Google Docs experienced a 6-hour outage affecting 45% of users when their OT transformation server hit a race condition during high-concurrency editing sessions. The issue occurred when multiple users rapidly edited the same paragraph while another user was applying complex formatting changes. Google's OT implementation couldn't correctly transform insertion operations against format changes, causing the transformation matrix to enter an inconsistent state. The server began rejecting all operations to prevent corruption, effectively locking documents in read-only mode. Google's post-mortem revealed they had to implement additional state validation and rollback 14 million document revisions. The fix involved adding operation commutativity checks and implementing a backup transformation pathway. This outage cost Google an estimated $10M in SLA credits and drove renewed interest in CRDT alternatives across the industry.

Napkin Math — Back of Envelope

Let's calculate OT server requirements for 100M daily active users: Average user types 1 character per second during active editing (10% of session time). With 2-hour average daily usage, that's 1 char/sec × 0.1 × 7200s = 720 operations per user per day. Total: 100M users × 720 ops = 72B operations/day = 833K ops/second average, 2.5M ops/second at peak. Each operation requires transformation against ~10 concurrent operations (average), so 25M transformations/second. At 100μs per transformation, we need 2,500 CPU cores just for OT compute. Add networking, persistence, and redundancy: ~10K cores total. At $0.04/core-hour on GCP, that's $3.5M/month just for conflict resolution. Memory: each active document needs ~50KB state, with 10M concurrent documents = 500GB RAM across the fleet.

Code — Key Algorithm
class OperationalTransform: def __init__(self): self.document = "" self.version = 0 def transform_insert_insert(self, op1, op2): """Transform two concurrent insert operations""" pos1, text1 = op1.position, op1.text pos2, text2 = op2.position, op2.text # If op2 inserts before op1's position, shift op1 right if pos2 <= pos1: return InsertOp(pos1 + len(text2), text1) else: return op1 # op1 position unchanged def transform_insert_delete(self, insert_op, delete_op): """Transform insert against delete operation""" ins_pos = insert_op.position del_pos, del_len = delete_op.position, delete_op.length # If delete is before insert position, shift insert left if del_pos + del_len <= ins_pos: return InsertOp(ins_pos - del_len, insert_op.text) # If delete starts after insert, no change needed elif del_pos >= ins_pos: return insert_op # If delete overlaps insert position, complex case else: # Insert at start of deleted region return InsertOp(del_pos, insert_op.text) def apply_operation(self, operation, remote_ops): """Apply operation after transforming against concurrent ops""" transformed_op = operation # Transform against all concurrent operations for remote_op in remote_ops: if isinstance(transformed_op, InsertOp): if isinstance(remote_op, InsertOp): transformed_op = self.transform_insert_insert( transformed_op, remote_op) elif isinstance(remote_op, DeleteOp): transformed_op = self.transform_insert_delete( transformed_op, remote_op) # Apply the transformed operation self._execute_operation(transformed_op) self.version += 1 return transformed_op class InsertOp: def __init__(self, position, text): self.position = position self.text = text class DeleteOp: def __init__(self, position, length): self.position = position self.length = length

This implementation shows the core OT transformation logic for handling concurrent insert and delete operations. The key insight is that operations must be transformed relative to each other to maintain intention preservation—if you intended to insert at position 5, but someone else inserted 3 characters at position 2, your operation should now insert at position 8. Real implementations handle dozens of operation types and complex transformation matrices.

Scale Progression
1K users:  Single OT server handles all transformations, operations stored in PostgreSQL, WebSocket connections direct to app servers. Simple conflict resolution with basic insert/delete operations.
1M users:  Sharded OT servers by document hash, Redis for operation queuing, separate transformation service cluster. Added differential sync and shadow document copies for offline support.
1B users:  Global OT server federation with regional clusters, Spanner for operation logs, custom networking protocol over HTTP/3. Hybrid OT+CRDT for partition tolerance, ML-based conflict prediction.

Interview Corner — FAANG-Level Questions
  1. Q: How would you handle a scenario where two users delete overlapping text ranges simultaneously in a collaborative editor?
    Model Answer: Transform the delete operations by computing the intersection and union of the ranges. The first operation deletes its full range, the second gets transformed to delete only the non-overlapping portion. Track the ordering using vector clocks to ensure deterministic results across all clients.
  2. Q: Why might you choose CRDTs over Operational Transform for a mobile collaborative app?
    Model Answer: CRDTs handle network partitions better since they don't require a central server for conflict resolution. Mobile apps frequently go offline, and CRDTs enable true local-first editing with seamless sync when connectivity returns. The memory overhead is acceptable on modern devices for the improved user experience.
  3. Q: What's the fundamental limitation of OT that makes it difficult to scale to hundreds of concurrent editors?
    Model Answer: OT transformation complexity grows quadratically with concurrent operations. Each operation must be transformed against every concurrent operation, creating O(n²) computational overhead. Additionally, the central server becomes a bottleneck and single point of failure as user count increases.
