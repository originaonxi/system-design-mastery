System 4/19: Google Docs Topic 6/6

Permission System at Scale

ACL for 3B+ Documents Across Organizations

Every second, Google Docs processes over 50,000 permission checks across 3+ billion documents, handling everything from a student's homework shared with a teacher to Fortune 500 board documents with complex organizational hierarchies. What makes this staggering is not just the scale, but that 99.95% of these checks complete in under 10ms while maintaining perfect security boundaries—a single permission leak could expose confidential data across millions of organizations.

The architecture separates hot path (ACL checks) from cold path (ACL modifications). Permission checks flow through Redis clusters backed by Bigtable for millisecond responses, while organizational changes propagate through Spanner's globally consistent database with eventual consistency to the cache layer.

How It Works — Deep Dive

Google's permission system operates on a hierarchical ACL model where each document maintains an Access Control List stored as a protocol buffer in Bigtable. The key innovation lies in their "effective permissions" computation—rather than traversing organizational hierarchies on every check, they pre-compute and cache flattened permission sets. When a user requests access to document ID "1BvR2F3X4...", the system first checks a distributed Redis cluster using the key pattern "acl:{doc_id}:{user_id}" which returns a cached permission bitmap (read=1, write=2, admin=4).

The cache miss scenario reveals the system's true complexity. The Permission Service queries Bigtable using row keys structured as "{doc_id}#{permission_type}" to retrieve the complete ACL. This includes direct grants ("user:john@company.com"), group memberships ("group:finance@company.com"), and domain-wide policies ("domain:company.com"). The service then performs a parallel lookup in Spanner to resolve group memberships and organizational hierarchy, since a user might inherit permissions through multiple paths—direct sharing, team membership, or organizational domain policies.

Group expansion presents the most significant computational challenge. A single permission check might require resolving nested groups up to 20 levels deep (the system limit to prevent infinite loops). Google optimizes this with a "group flattening" service that runs async batch jobs every 10 minutes, pre-computing transitive group memberships and storing them in a separate Bigtable column family. This transforms an O(n²) group resolution into an O(1) lookup, critical when processing 50K+ permission checks per second.

The system handles permission inheritance through a concept called "effective ACLs." When computing permissions, the service combines document-level ACLs with folder-level ACLs and organization-level policies using a priority system: explicit deny > explicit allow > inherited allow > default deny. This computation happens in the Permission Service using a Java-based rules engine that processes ACL protocol buffers through a series of filters and transformers, ultimately producing a cached permission bitmap valid for 24 hours.

Real-time permission updates leverage Google's Pub/Sub system with a twist—they use "negative caching" to handle revocations. When permissions are revoked, instead of immediately updating all cache entries (which could take hours), they publish revocation events that create negative cache entries. The Permission Service checks both positive and negative caches, ensuring revoked access takes effect within seconds rather than waiting for cache expiration.

Real Obstacle — What Actually Went Wrong

In March 2019, Google experienced a 4-hour outage affecting Google Drive and Docs permissions after a routine Bigtable cluster maintenance. The issue started when a single Bigtable tablet server experienced a hardware failure during the maintenance window. The tablet contained permission data for documents with IDs starting with "1A" through "1F"—approximately 180 million documents. While Bigtable's replication should have handled this gracefully, a bug in the tablet splitting logic caused the replacement tablet to inherit corrupted row keys. Users could access documents but couldn't share them, and new documents appeared to be "owned by nobody." The incident cost Google an estimated $14M in SLA credits and revealed a fundamental flaw in their permission system's dependency on single points of failure. The fix required rebuilding the affected tablet from transaction logs while implementing emergency read-only mode, and led to architectural changes that distributed permission metadata across multiple tablet servers per document.

Napkin Math — Back of Envelope

Let's calculate storage and compute requirements for 3B documents with permissions:

Storage: 3B documents × 2KB average ACL size = 6TB for raw ACL data. With 3x replication in Bigtable = 18TB. Add group membership data (500M users × 50 groups avg × 100 bytes) = 2.5TB. Total: ~25TB.

Cache: 50K queries/sec × 80% unique document-user pairs × 200 bytes cached data × 86400 sec/day × 0.3 retention = 207GB daily cache. With Redis memory overhead (3x) = ~600GB Redis cluster.

Compute: 50K QPS with 3% cache miss = 1,500 Bigtable queries/sec. Each query averages 2ms × 1,500 = 3,000ms of query time per second. Need 4-5 dedicated query servers to handle cache misses, plus 20+ servers for cache hits and group resolution.

Code — Key Algorithm
import hashlib from enum import IntFlag from typing import Dict, Set, Optional class Permission(IntFlag): READ = 1 WRITE = 2 ADMIN = 4 SHARE = 8 class ACLResolver: def __init__(self, cache, bigtable_client, group_service): self.cache = cache self.bigtable = bigtable_client self.group_service = group_service def check_permission(self, doc_id: str, user_id: str, required: Permission) -> bool: # Check cache first cache_key = f"acl:{doc_id}:{user_id}" cached_perms = self.cache.get(cache_key) if cached_perms is not None: return bool(cached_perms & required) # Cache miss - compute effective permissions effective_perms = self._compute_effective_permissions( doc_id, user_id) # Cache for 24 hours self.cache.setex(cache_key, 86400, effective_perms.value) return bool(effective_perms & required) def _compute_effective_permissions(self, doc_id: str, user_id: str) -> Permission: # Fetch ACL from Bigtable acl_data = self.bigtable.get_row(f"acl#{doc_id}") permissions = Permission(0) # Direct user permissions if f"user:{user_id}" in acl_data: permissions |= Permission(acl_data[f"user:{user_id}"]) # Group-based permissions user_groups = self.group_service.get_flattened_groups(user_id) for group in user_groups: if f"group:{group}" in acl_data: permissions |= Permission(acl_data[f"group:{group}"]) # Domain-wide permissions domain = user_id.split('@')[1] if f"domain:{domain}" in acl_data: permissions |= Permission(acl_data[f"domain:{domain}"]) return permissions

This code implements the core permission checking algorithm using bitwise flags for efficient permission combinations. The cache-first approach with fallback to computed permissions mirrors Google's actual implementation, while the flattened group lookup avoids expensive recursive group resolution during permission checks.

Scale Progression
1K users:  Single PostgreSQL database with simple ACL tables, in-memory cache, synchronous group lookups. Basic owner/viewer/editor model sufficient.
1M users:  Sharded MySQL with Redis cluster, async group flattening jobs, separate read/write paths. Introduction of organizational hierarchies and bulk permission operations.
1B users:  Bigtable + Spanner architecture, global Redis clusters, negative caching, pre-computed permission bitmaps. Complex nested group resolution with circuit breakers and fallback mechanisms.

Interview Corner — FAANG-Level Questions
  1. Q: How would you handle permission inheritance when a user belongs to multiple groups with conflicting permissions?
    Model Answer: Implement explicit precedence rules (deny > allow), use permission bitmasks for efficient computation, and maintain audit logs for debugging conflicts. Consider context-aware permissions where location or time might influence access.
  2. Q: Design a permission system that can revoke access to 1 million documents instantly when an employee is terminated.
    Model Answer: Use negative caching with pub/sub for real-time revocation events, implement user-based cache invalidation patterns, and maintain separate "revoked users" bitmap that's checked before permission grants. Cache at the user level, not document level.
  3. Q: How do you prevent the thundering herd problem when a popular document's permissions are updated?
    Model Answer: Implement cache warming through async batch jobs, use probabilistic cache expiration (add jitter), and employ circuit breakers with stale-while-revalidate patterns. Consider document popularity scoring to pre-warm high-traffic items.
