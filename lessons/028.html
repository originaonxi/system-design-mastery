Kafka Core Architecture

Brokers, Topics, Partitions, Consumer Groups Explained

In 2011, LinkedIn was processing 1 billion unique messages per day through a homegrown messaging system that was buckling under load. Jay Kreps and his team built Apache Kafka to handle 2 trillion messages per day at sub-10ms latency — a system so robust that it now powers the data infrastructure for over 80% of Fortune 100 companies. Understanding Kafka's distributed commit log architecture is essential for any engineer designing event-driven systems at scale.

How It Works — Deep Dive

Kafka's architecture is built around the concept of a distributed commit log, where each topic is an ordered, immutable sequence of records that are continually appended to. When a producer sends a message, it's written to exactly one partition within a topic, determined either by an explicit partition key hash or round-robin assignment. The partition leader (one of the broker replicas) receives the write, appends it to its local log segment file, and coordinates replication to follower replicas. This design achieves both horizontal scalability through partitioning and fault tolerance through replication, with typical deployments using a replication factor of 3 to survive up to 2 broker failures.

The broker cluster uses Apache ZooKeeper (or KRaft in Kafka 2.8+) for distributed coordination, maintaining critical metadata like partition leadership assignments, broker membership, and topic configurations. When a partition leader fails, ZooKeeper triggers an automatic failover election among the in-sync replicas (ISR), promoting a follower to leader typically within 30-50ms. The ISR mechanism ensures data consistency by only committing writes once they're replicated to all in-sync followers, though producers can choose different acknowledgment levels (acks=0 for fire-and-forget, acks=1 for leader confirmation, acks=all for full ISR confirmation) to trade latency for durability guarantees.

Consumer groups provide Kafka's scalability mechanism for message consumption, automatically distributing partition assignments across group members using a partition assignment strategy (range, round-robin, sticky, or custom). Each partition is consumed by exactly one consumer within a group, meaning you can scale consumption up to the number of partitions. The group coordinator (one of the brokers) manages consumer membership through periodic heartbeats (default 3-second intervals) and triggers rebalancing when consumers join or leave. During rebalancing, all consumers stop processing and negotiate new partition assignments, causing brief processing delays that can be minimized through careful consumer group sizing and sticky assignment strategies.

Kafka's storage layer uses a segmented log structure where each partition is stored as a series of segment files (default 1GB each) containing batched records. The active segment receives new writes while older segments are immutable, enabling efficient cleanup policies like time-based retention (default 7 days) or size-based retention. Each segment includes an index file mapping logical offsets to physical file positions, allowing O(1) random access for consumer reads. The entire system is designed for sequential disk I/O, leveraging the OS page cache aggressively — a properly configured Kafka cluster can achieve 750MB/s sustained throughput per broker with median latencies under 5ms.

The protocol layer implements a custom binary protocol over TCP, with producers and consumers maintaining persistent connections to brokers and batching requests for efficiency. Producers buffer records locally (default 16KB batches or 5ms linger time) before sending, while consumers fetch records in configurable batch sizes (default 1MB). The fetch protocol includes sophisticated features like incremental fetch sessions to minimize metadata overhead and follower fetching optimization to reduce cross-datacenter bandwidth in multi-region deployments. Kafka 2.1+ includes support for exactly-once semantics through idempotent producers and transactional messaging, using epoch numbers and sequence IDs to detect and eliminate duplicate records at the broker level.

Real Obstacle — What Actually Went Wrong

In March 2020, a major financial services company experienced a catastrophic Kafka outage during market opening hours, costing approximately $2.3M in lost trading revenue over 90 minutes. The incident began when a routine broker restart triggered a cascade of rebalancing across 847 consumer groups processing real-time market data. The root cause was consumer group session timeouts set too aggressively at 5 seconds, combined with a consumer lag spike that caused the rebalancing protocol to enter an infinite loop — consumers would join the group, get partition assignments, fall behind due to the backlog, time out, and repeat. The engineering team's fix involved temporarily increasing session.timeout.ms to 30 seconds and max.poll.interval.ms to 5 minutes, then implementing a staged restart procedure and consumer lag monitoring to prevent future cascading failures. This incident led to industry-wide adoption of chaos engineering practices specifically for Kafka consumer group testing.

This code implements Kafka's core partition assignment algorithms: the murmur2 hash-based partitioner that producers use to determine which partition receives each message, and the range assignment strategy that consumer group coordinators use to distribute partitions among group members. The partitioner ensures even distribution while maintaining key ordering within partitions, while the consumer assignment algorithm minimizes rebalancing when consumers join or leave the group.

Interview Corner — FAANG-Level Questions
  1. Q: How would you handle a situation where a Kafka consumer group is experiencing constant rebalancing?
    Model Answer: I'd investigate session.timeout.ms and max.poll.interval.ms configurations, check for consumer processing bottlenecks causing poll timeouts, and examine partition count vs consumer count ratios. The solution typically involves increasing timeouts, optimizing consumer processing logic, or implementing incremental cooperative rebalancing.
  2. Q: Explain how Kafka achieves exactly-once semantics and when you might not want to use it.
    Model Answer: Kafka uses idempotent producers with sequence numbers and transactional messaging across partitions to prevent duplicates. You might avoid it when the performance cost (20-30% throughput reduction) outweighs the benefit, or when your downstream systems are naturally idempotent and can handle occasional duplicates more efficiently.
  3. Q: Design partition strategy for a topic that needs to maintain user session ordering while maximizing parallelism.
    Model Answer: Use user ID as the partition key to ensure all events for a user go to the same partition, size partitions based on user distribution analysis, and consider composite keys (user_id + session_id) if sessions are independent. Monitor partition skew and implement custom partitioners if needed to handle hot users.
