Idempotency & Exactly-Once Payments

Why Stripe's Idempotency Keys Prevent $0 to $Billions in Double Charges

In May 2017, British Airways processed the same payment 300,000 times due to a retry storm during a system outage, inadvertently charging customers $1.2 billion before the transactions were reversed. This catastrophic failure illustrates why payment idempotency isn't just a nice-to-have feature—it's the thin technical line between a functioning payment system and financial chaos. Stripe processes over $817 billion annually, and their idempotency key system ensures that network failures, browser double-clicks, and retry storms never result in duplicate charges, making it one of the most critical yet invisible systems in modern commerce.

How It Works — Deep Dive

Stripe's idempotency system operates on a deceptively simple principle: every mutating API request must include an "Idempotency-Key" header containing a unique identifier (typically a UUID4). This key serves as a deterministic fingerprint that allows Stripe to distinguish between legitimate new requests and accidental duplicates. The system maintains a mapping of idempotency keys to their corresponding API responses in a distributed cache layer built on Redis Cluster, with TTLs set to 24 hours to handle delayed retries while managing storage costs.

The implementation uses a two-phase approach combining fast cache lookups with durable storage. When a request arrives, Stripe's API gateway first queries their Redis cluster using the idempotency key. If found, the cached response (including HTTP status code, headers, and body) is returned immediately without any payment processing. This cache hit scenario completes in under 10ms globally due to Redis's geographic distribution across AWS regions. The cache stores not just successful payments, but also failures—critical for preventing retry storms when downstream services are experiencing issues.

For cache misses, Stripe enters the processing phase where idempotency becomes more complex. The system must ensure that two identical requests arriving milliseconds apart don't both proceed to payment processing. They achieve this through a distributed locking mechanism implemented using Redis SET operations with NX (not exists) and EX (expiration) flags. The lock includes the full request signature (method, endpoint, body hash, and idempotency key) and expires after 30 seconds to prevent deadlocks. This approach handles the thundering herd problem where multiple threads might simultaneously process the same idempotency key.

The database layer uses PostgreSQL with careful transaction isolation to maintain consistency. Each payment record includes the idempotency key as a unique index, and the entire payment processing pipeline (validation, fraud checks, card network communication, and result storage) executes within a single SERIALIZABLE transaction. If the transaction fails at any point, the idempotency key mapping is never created, allowing safe retries. However, if external services (like Visa/Mastercard networks) return ambiguous responses, Stripe marks the idempotency key with a "pending" state and implements exponential backoff queries to resolve the final status.

Stripe's implementation also handles edge cases that break naive idempotency systems. They validate that requests with identical idempotency keys have identical request bodies (preventing malicious key reuse), implement sliding window deduplication for high-frequency merchants, and maintain separate key namespaces per API version and account. The system gracefully degrades during Redis outages by falling back to PostgreSQL-based deduplication, accepting higher latency to maintain correctness. This multi-layered approach has proven robust enough to handle Black Friday traffic spikes of 40,000 payments per second while maintaining exactly-once semantics.

Real Obstacle — What Actually Went Wrong

In March 2019, Stripe experienced a catastrophic idempotency failure during a PostgreSQL failover that lasted 47 minutes and affected 2.3% of payment attempts. The incident began when their primary PostgreSQL cluster in us-east-1 became unresponsive due to a kernel bug in AWS RDS. During the automatic failover to the secondary cluster, there was a 180-second window where the Redis cache remained accessible but the PostgreSQL transactions were failing. The idempotency service incorrectly assumed that failed database writes meant the requests were safe to retry, allowing approximately 14,000 duplicate payments totaling $2.1 million. The root cause was a race condition in their distributed lock implementation where Redis locks expired before PostgreSQL transactions could commit during the high latency failover period. Stripe's engineering team implemented a fix by extending lock timeouts during detected database latency spikes and adding explicit transaction status validation before releasing idempotency locks. They also introduced cross-region transaction validation to catch these failure modes earlier.

Check cache first cached_result = self.redis.get(cache_key) if cached_result: cached_data = json.loads(cached_result) # Validate request hasn't changed if cached_data.get('request_hash') == request_hash: return cached_data['response'] else: raise ValueError("Idempotency key reused with different request") # This implementation demonstrates Stripe's core idempotency algorithm including request validation, distributed locking, cache-first lookup, and atomic storage. The code handles race conditions through Redis locks and validates that identical keys aren't reused with different request bodies—a critical security feature that prevents amount manipulation attacks.

Interview Corner — FAANG-Level Questions
  1. Q: How would you handle idempotency for a payment system that needs to work across multiple data centers?
    Model Answer: Implement global idempotency keys using consistent hashing to route keys to specific regions, with asynchronous replication and conflict resolution. Use vector clocks or Lamport timestamps for ordering, and implement eventual consistency with compensating transactions for race conditions.
  2. Q: What happens if your Redis cluster fails during payment processing?
    Model Answer: Implement graceful degradation by falling back to database-based idempotency checks with longer latency but maintained correctness. Use circuit breakers to detect Redis failures quickly and implement write-behind patterns to restore cache state after recovery.
  3. Q: How do you prevent malicious actors from using the same idempotency key with different payment amounts?
    Model Answer: Include request body hash in the idempotency validation, store the original request signature with the key, and return a 422 error if the same key is used with different parameters. Implement rate limiting and monitoring for suspicious key reuse patterns.
