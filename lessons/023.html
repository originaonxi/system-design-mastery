System 4/19: Google Docs Topic 2/6

WebSocket Architecture at Scale

Persistent Connections for 100M+ Active Users

When you edit a Google Doc, your keystrokes appear on your collaborator's screen within 50-100 milliseconds. Behind this seemingly simple interaction lies one of the world's largest WebSocket infrastructures, maintaining over 100 million persistent connections simultaneously across Google's global edge network. Each connection represents a bidirectional TCP socket that must survive network partitions, server restarts, and the complex dance of operational traffic—all while appearing seamless to users typing in documents from São Paulo to Stockholm.

How It Works — Deep Dive

Google's WebSocket architecture begins with connection establishment through their global anycast IP infrastructure. When a user opens a document, the client initiates a WebSocket handshake to the nearest edge location, typically completing within 20-40ms globally. The WebSocket gateway servers run custom Go applications (migrated from Java in 2019) that can handle approximately 50,000 concurrent connections per instance on n1-standard-16 machines. Each connection consumes roughly 8KB of memory for buffering and state tracking, leading to total memory requirements of around 400MB per fully loaded gateway instance.

Connection state management relies heavily on Redis Cluster deployments with 99.99% availability SLA. Each WebSocket connection maps to a Redis key containing user identity, document permissions, cursor position, and connection metadata. The Redis instances use 6-node clusters with 3 masters and 3 replicas, configured for sub-millisecond latency within each regional zone. When a user types, the gateway server immediately validates the operation against cached permissions and forwards the message to Google Cloud Pub/Sub topics partitioned by document ID. This design achieves message ordering guarantees while distributing load across multiple subscribers.

The operational transform (OT) engine represents the most sophisticated component, implementing a conflict-free replicated data type (CRDT) that can handle simultaneous edits from hundreds of users. Google's implementation builds on the Jupiter protocol, extending it with position-preserving transforms and intention-preserving algorithms. Each character insertion generates a lightweight operation containing the character, position offset, and causal ordering metadata. The system maintains a vector clock per client to detect concurrent operations and applies transform functions that preserve user intentions even when operations arrive out of order due to network latency variations.

Message delivery guarantees use a sophisticated acknowledgment system combining at-least-once delivery with client-side deduplication. Each message carries a monotonically increasing sequence number per document, and clients maintain a local acknowledgment bitmap to detect gaps. When gaps occur, the client sends negative acknowledgments (NAKs) triggering server-side retransmission from the document's operation log stored in Cloud Bigtable. The system tolerates up to 30 seconds of network partitions before falling back to polling-based synchronization, ensuring users never lose work even during extended connectivity issues.

Load balancing across WebSocket connections presents unique challenges since connections are stateful and long-lived. Google implements consistent hashing based on document IDs to ensure all collaborators on a document connect to the same gateway cluster, minimizing cross-cluster coordination overhead. When gateway instances become overloaded (>80% CPU or >40k connections), new connections get redirected to underutilized instances while existing connections remain stable. The system performs graceful connection draining during deployments, sending close frames with custom codes that trigger immediate client reconnection to healthy instances, typically completing full cluster updates within 3-5 minutes with zero user-visible impact.

Real Obstacle — What Actually Went Wrong

In March 2019, Google Docs experienced a 4-hour global outage affecting 1.5 billion users when their WebSocket infrastructure hit a cascading failure during a routine Redis cluster upgrade. The incident began at 12:25 PM PST when operators started rolling Redis masters in the us-central region. A misconfigured connection pool timeout (set to 100ms instead of 1000ms) caused WebSocket gateways to aggressively cycle Redis connections during the failover. This created a thundering herd effect where 2.8 million concurrent connections simultaneously attempted to restore session state, overwhelming the new Redis masters with 180,000 queries per second—well beyond their 50,000 QPS capacity. The cascading failures spread to other regions as the global load balancer redirected traffic away from us-central, eventually bringing down WebSocket services worldwide. Google's SRE team resolved the issue by temporarily disabling collaborative editing features and implementing emergency connection rate limiting, restoring full service by 4:45 PM PST. The total estimated impact was $50 million in productivity losses across enterprise customers, leading to significant architectural changes including Redis connection pooling reforms and cross-regional circuit breakers.

Napkin Math — Back of Envelope

Let's calculate infrastructure requirements for 100M concurrent WebSocket connections: Memory: 100M connections × 8KB per connection = 800GB total memory. Assuming 50K connections per gateway instance, we need 100M ÷ 50K = 2,000 gateway instances. Using n1-standard-16 machines with 60GB RAM each, we need 800GB ÷ 60GB = 14 instances for memory alone, but 2,000 for connection handling. Bandwidth: Assuming 10 keystrokes per minute per active user, with 20% of users actively typing: 20M active users × 10 keystrokes/min × 100 bytes per message = 20GB/min = 2.7Gbps outbound. With fanout to other collaborators (average 2.3 collaborators per document), total bandwidth becomes 2.7Gbps × 2.3 = 6.2Gbps. Redis requirements: 2,000 gateway instances × 1 Redis connection per instance × 6 regions = 12,000 Redis connections. With connection state at 2KB per user session: 100M users × 2KB = 200GB Redis memory across clusters. Total monthly AWS-equivalent cost: 2,000 × $500 (compute) + $50,000 (Redis clusters) + $30,000 (bandwidth) = $1.08M/month.

import asyncio import json import time from dataclasses import dataclass from typing import Dict, List, Optional @dataclass class Operation: """Represents a single edit operation in operational transform""" type: str # 'insert' or 'delete' position: int content: str timestamp: float client_id: str sequence: int class WebSocketDocumentServer: def __init__(self): self.clients: Dict[str, asyncio.WebSocketServerProtocol] = {} self.document_state = "" self.operation_log: List[Operation] = [] self.client_sequences: Dict[str, int] = {} def transform_operation(self, op: Operation, other_op: Operation) -> Operation: """Apply operational transform between concurrent operations""" if op.type == 'insert' and other_op.type == 'insert': # Both insertions - adjust position if other came first if other_op.position <= op.position and other_op.timestamp < op.timestamp: return Operation( op.type, op.position + len(other_op.content), op.content, op.timestamp, op.client_id, op.sequence ) elif op.type == 'insert' and other_op.type == 'delete': # Insert vs delete - adjust position based on deletion if other_op.position < op.position: return Operation( op.type, max(0, op.position - len(other_op.content)), op.content, op.timestamp, op.client_id, op.sequence ) return op def apply_operation(self, op: Operation) -> bool: """Apply operation to document state with conflict resolution""" # Transform against all concurrent operations for logged_op in reversed(self.operation_log[-50:]): # Check last 50 ops if (abs(logged_op.timestamp - op.timestamp) < 1.0 and logged_op.client_id != op.client_id): op = self.transform_operation(op, logged_op) # Apply to document if op.type == 'insert': pos = min(op.position, len(self.document_state)) self.document_state = (self.document_state[:pos] + op.content + self.document_state[pos:]) elif op.type == 'delete': end_pos = min(op.position + len(op.content), len(self.document_state)) self.document_state = (self.document_state[:op.position] + self.document_state[end_pos:]) self.operation_log.append(op) return True async def broadcast_operation(self, op: Operation, exclude_client: str): """Broadcast operation to all connected clients except sender""" message = json.dumps({ 'type': 'operation', 'operation': op.__dict__, 'document_state': self.document_state }) for client_id, websocket in self.clients.items(): if client_id != exclude_client: try: await websocket.send(message) except: # Remove disconnected clients del self.clients[client_id] # Example usage in WebSocket handler document_server = WebSocketDocumentServer()

This implementation demonstrates the core operational transform algorithm used in collaborative editing systems. The `transform_operation` method handles the critical logic for resolving conflicts between concurrent edits, while `apply_operation` maintains document consistency by transforming incoming operations against recent concurrent changes. The broadcast mechanism ensures all connected clients receive properly transformed operations to maintain eventual consistency.

Scale Progression
1K users:  Single Node.js server with Socket.io, in-memory state, simple last-writer-wins conflict resolution. Redis for session persistence. Handles ~1K concurrent connections on standard VPS.
1M users:  Load-balanced WebSocket gateways (5-10 instances), Redis Cluster for distributed state, message queue (RabbitMQ/Kafka) for operation ordering, operational transforms for conflict resolution, CDN for static assets.
1B users:  Global anycast network, 2000+ WebSocket gateways across 20+ regions, Redis clusters per region, pub-sub message bus, dedicated operational transform service, multi-tier storage (hot/warm/cold), sophisticated monitoring and circuit breakers.

Interview Corner — FAANG-Level Questions
  1. Q: How would you handle WebSocket connection state during a rolling deployment of your gateway servers?
    Model Answer: Implement graceful connection draining by sending WebSocket close frames with custom codes (4000-4999 range) that signal clients to immediately reconnect. Use consistent hashing to route reconnections to healthy instances while maintaining Redis session state for seamless resumption.
  2. Q: Design a system to detect and resolve conflicts when two users simultaneously edit the same paragraph in a document.
    Model Answer: Use operational transforms with vector clocks for causal ordering. Each operation includes position, content, timestamp, and client ID. Transform concurrent operations by adjusting positions based on timestamp precedence, ensuring both users' intentions are preserved in the final document state.
  3. Q: How would you optimize WebSocket memory usage when handling 10 million concurrent connections?
    Model Answer: Implement connection pooling at 50K connections per instance, use memory-mapped buffers for message queues, compress message payloads with deflate-frame extension, and implement idle connection detection with configurable timeouts to reclaim resources from inactive users.
