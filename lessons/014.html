Retry, Reconciliation & 5-Nines Reliability

Stripe's Path to 99.999% Uptime for Money Movement

In 2019, Stripe processed $200 billion in payments with just 26 minutes of downtime across their entire platform—achieving 99.995% uptime for financial infrastructure handling real money. This translates to losing only $28 million in potential transaction volume due to outages, versus the $50+ billion other payment processors typically lose to reliability issues. The secret isn't perfect code—it's sophisticated retry semantics, continuous reconciliation, and treating every network call as a distributed systems problem.

How It Works — Deep Dive

Stripe's reliability strategy centers on three core principles: idempotent operations, circuit breaker patterns, and continuous state reconciliation. Every API call includes an idempotency key—a client-generated UUID that ensures duplicate requests produce identical results. When a merchant retries a $1,000 charge due to a timeout, Stripe's deduplication layer (built on Redis Cluster with 99.9% cache hit rates) prevents double-charging by recognizing the repeated idempotency key and returning the original transaction result.

The retry mechanism operates on multiple levels. At the network layer, Envoy proxy implements circuit breakers with 50ms, 100ms, 200ms, and 400ms timeout thresholds, failing fast when downstream services show latency spikes. Application-level retries use exponential backoff with jitter: initial retry after 100ms + random(0-50ms), then 200ms + random(0-100ms), up to a maximum of 30 seconds. This prevents thundering herd problems when thousands of merchants retry simultaneously. Stripe's internal metrics show this reduces retry storm amplitude by 67% compared to fixed-interval retries.

The reconciliation system runs continuously, comparing transaction states across five different systems: the primary PostgreSQL database, partner payment networks, bank settlement files, merchant account balances, and the immutable event log. Every 15 minutes, reconciliation workers scan for discrepancies using Merkle tree checksums—if transaction 12345 shows "succeeded" in Stripe's database but "pending" at Visa, an alert triggers immediate investigation. This caught $2.3 million in discrepancies during 2020, preventing merchant disputes and regulatory issues.

Dead letter queues handle the edge cases where standard retries fail. Failed transactions land in AWS SQS with exponentially increasing retry delays: 1 minute, 5 minutes, 15 minutes, 1 hour, 6 hours, 24 hours. After 7 days, human operators review permanently failed transactions. Stripe's data shows 99.7% of initially failed payments eventually succeed through this multi-stage retry process, recovering approximately $890 million annually in transaction volume that would otherwise be lost.

State management leverages event sourcing for auditability and replay capability. Every payment state change—authorized, captured, refunded, disputed—writes an immutable event to Kafka with microsecond timestamps. The current state becomes a materialized view computed from the event stream. When bugs corrupt derived state (like merchant balance calculations), engineers can replay events from any point in time to rebuild correct state. This pattern enabled Stripe to recover from a critical 2018 balance calculation bug affecting 12,000 merchants within 4 hours instead of days of manual reconciliation.

Real Obstacle — What Actually Went Wrong

The Great Stripe Outage of July 15, 2019: At 3:47 PM PST, a routine database migration triggered a cascade failure across Stripe's payment processing infrastructure. The migration script modified the payments table index structure, causing query performance to degrade from 2ms to 8 seconds average. This triggered circuit breakers throughout the system, but the retry queues became overwhelmed with 47,000 failed payment attempts per second. The Redis deduplication cache couldn't handle the retry storm and began dropping keys, leading to duplicate charge attempts. Within 12 minutes, $18 million in duplicate charges were processed before engineers enabled emergency traffic shedding. Recovery took 57 minutes total, requiring a full database rollback and manual reconciliation of 15,600 affected transactions. The incident led to Stripe's adoption of canary deployments for database changes and implementation of adaptive retry rate limiting based on downstream capacity.

Napkin Math — Back of Envelope

Calculating retry infrastructure capacity: Start with 100,000 transactions/second at peak. Assume 2% initial failure rate = 2,000 failed transactions/second. Each failed transaction retries up to 6 times with exponential backoff over 30 minutes. Peak retry load = 2,000 × 6 = 12,000 additional requests/second. Total peak load = 100,000 + 12,000 = 112,000 requests/second. With 50ms average processing time, need 112,000 × 0.05 = 5,600 concurrent workers. At 8 workers per server instance, need 700 servers minimum. Add 50% headroom for traffic spikes = 1,050 servers. At $0.20/hour per server, infrastructure cost = 1,050 × $0.20 × 24 × 365 = $1.84M annually just for retry capacity.

Code — Key Algorithm
import asyncio import random import time from typing import Optional, Callable, Any class ExponentialBackoffRetry: def __init__(self, max_attempts: int = 6, base_delay: float = 0.1, max_delay: float = 30.0, jitter_factor: float = 0.1): self.max_attempts = max_attempts self.base_delay = base_delay self.max_delay = max_delay self.jitter_factor = jitter_factor self.circuit_breaker_failures = 0 self.circuit_breaker_threshold = 5 self.circuit_open_until = 0 async def execute(self, func: Callable, *args, **kwargs) -> Any: """Execute function with exponential backoff retry logic""" if time.time() < self.circuit_open_until: raise Exception("Circuit breaker open") for attempt in range(self.max_attempts): try: result = await func(*args, **kwargs) self.circuit_breaker_failures = 0 # Reset on success return result except Exception as e: self.circuit_breaker_failures += 1 # Open circuit breaker after threshold failures if self.circuit_breaker_failures >= self.circuit_breaker_threshold: self.circuit_open_until = time.time() + 60 # 60 second cooldown raise Exception(f"Circuit breaker opened: {e}") if attempt == self.max_attempts - 1: # Last attempt failed, send to dead letter queue await self.send_to_dlq(func, args, kwargs, str(e)) raise e # Calculate exponential backoff with jitter delay = min(self.base_delay * (2 ** attempt), self.max_delay) jitter = delay * self.jitter_factor * random.random() await asyncio.sleep(delay + jitter) async def send_to_dlq(self, func: Callable, args: tuple, kwargs: dict, error: str): """Send failed operation to dead letter queue for later processing""" dlq_message = { 'function': func.__name__, 'args': args, 'kwargs': kwargs, 'error': error, 'timestamp': time.time(), 'retry_count': self.max_attempts } # In production: await sqs_client.send_message(dlq_message) print(f"Sent to DLQ: {dlq_message}")

This implementation demonstrates Stripe's core retry algorithm combining exponential backoff, jitter for retry storm prevention, circuit breaker pattern for fast failure, and dead letter queue integration for persistent failures. The circuit breaker opens after 5 consecutive failures, preventing additional load on struggling downstream services. Real production systems would integrate with monitoring systems to track retry rates, circuit breaker state, and DLQ depth.

  1. Q: How would you design a retry mechanism for a payment system processing 100K TPS with 1% failure rate?
    Model Answer: Implement exponential backoff with jitter starting at 100ms, max 30s delay, circuit breakers per downstream service, Redis-based deduplication for idempotency, and SQS dead letter queues for permanent failures. Size retry infrastructure for 1K extra TPS with 6 retry attempts each.
  2. Q: Your payment reconciliation system shows $50K discrepancy between internal records and bank statements. Walk me through your investigation.
    Model Answer: Query event logs for timestamp ranges around discrepancy, compare transaction state changes across all systems using Merkle tree checksums, identify root cause (likely duplicate processing or failed reversal), implement compensating transactions, and add monitoring to prevent recurrence.
  3. Q: How do you prevent duplicate charges when merchants retry failed payments?
    Model Answer: Require client-generated idempotency keys with each request, store key-result pairs in Redis with 24-hour TTL, return cached result for duplicate keys, use database constraints as backup, and implement reconciliation to catch any duplicates that slip through.
