System 3/19: YouTube Topic 2/7

Content Delivery Network (CDN)

100+ Edge Locations Serving 1B Hours of Video Daily

Every time you click play on a YouTube video, you're triggering one of the most sophisticated content delivery systems ever built. YouTube's CDN serves over 1 billion hours of video daily across 100+ edge locations, with 95% of requests served from cache and sub-100ms latency worldwide. This isn't just about faster video loading—it's about a globally distributed system that must handle 4K streams, live broadcasts, and viral content spikes while maintaining consistent quality of experience across six continents.

This architecture shows YouTube's multi-tier CDN system. Client requests hit the nearest edge cache (L1), which maintains hot content in RAM. Cache misses flow to regional Points of Presence (PoPs) that serve as L2 caches with larger SSD storage. The global load balancer routes requests based on geography, server health, and content availability. Origin servers in Google Cloud Storage hold the master copies, while the encoding pipeline generates multiple bitrate versions for adaptive streaming.

How It Works — Deep Dive

YouTube's CDN operates on a hierarchical caching model with sophisticated cache management algorithms. When a user requests a video, the system first checks the L1 edge cache using a consistent hashing algorithm based on the video ID. The edge servers run nginx with custom modules for video streaming, maintaining approximately 32GB of RAM cache for the hottest content and 2TB of SSD storage for warm content. Cache decisions use a modified Least Recently Used (LRU) algorithm that factors in content popularity predictions from YouTube's recommendation system, geographic viewing patterns, and file size optimization.

The video delivery process leverages HTTP/2 server push and HTTP Live Streaming (HLS) protocols. Each video is encoded into multiple representations using H.264 and VP9 codecs at bitrates ranging from 144p (80 kbps) to 4K (45 Mbps). The Adaptive Bitrate (ABR) algorithm continuously monitors client bandwidth and adjusts quality in real-time. YouTube's ABR implementation uses a buffer-based approach with lookahead optimization, maintaining 10-30 seconds of video in the client buffer while predicting network conditions using exponential smoothing of throughput measurements.

Cache invalidation presents unique challenges for video content. YouTube implements a push-based invalidation system where origin servers broadcast cache updates through Apache Kafka message queues to all edge locations. For live streams, the system uses chunked transfer encoding with 2-6 second segments, requiring sub-second propagation of new content chunks. The invalidation protocol uses vector clocks to handle out-of-order updates and ensure consistency across geographically distributed caches.

Geographic routing relies on anycast IP addressing combined with BGP route optimization. Each edge location announces the same IP prefixes, allowing routers to automatically direct traffic to the nearest healthy PoP. YouTube enhances this with application-layer routing decisions based on real-time latency measurements. The system maintains a global view of server health through a distributed monitoring system that performs synthetic video requests every 30 seconds from each edge location, measuring both connection establishment time and video start delay.

The CDN's storage tier uses a combination of hot, warm, and cold storage optimized for video access patterns. Hot content (watched within the last 24 hours) stays in RAM across multiple edge servers. Warm content (last 30 days) resides on local SSDs with LZ4 compression achieving 2:1 compression ratios without CPU overhead. Cold content moves to regional storage clusters with higher compression ratios but longer retrieval times. The system uses machine learning models trained on historical viewing data to predict content temperature transitions, pre-positioning content before demand spikes.

Real Obstacle — What Actually Went Wrong

On December 14, 2020, YouTube experienced a global outage lasting 45 minutes that affected millions of users worldwide. The root cause was a misconfigured authentication service update that cascaded through Google's identity system. While the core YouTube infrastructure remained healthy, the CDN edge servers couldn't validate user authentication tokens, causing video requests to fail with HTTP 500 errors. The incident cost an estimated $1.65 million in lost ad revenue and highlighted the critical dependency between CDN performance and centralized authentication services. Google's post-mortem revealed that their canary deployment process failed to catch the edge case where cached authentication tokens expired simultaneously across multiple data centers during a routine certificate rotation. The fix required rolling back the authentication service changes and implementing circuit breakers to gracefully degrade service when auth systems are unavailable, allowing anonymous video playback to continue during similar failures.

Napkin Math — Back of Envelope

Let's calculate YouTube's CDN requirements: 1 billion hours daily = 41.7M concurrent streams. Average video bitrate of 2 Mbps = 83.4 Tbps total bandwidth. With 100 edge locations, each handles ~834 Gbps average. Accounting for 5:1 peak-to-average ratio = 4.2 Tbps peak per major region. Storage requirements: 500 hours uploaded per minute × 2GB average per hour × multiple bitrate copies (5x) = 5TB/minute of new content. With 30-day edge cache retention and 70% deduplication, each edge location needs ~108TB storage capacity. RAM requirements: 95% cache hit rate with 32GB RAM per server means hot content fits in ~3.2TB distributed across 100 servers per PoP.

Code — Key Algorithm
import hashlib import time from typing import Dict, List, Optional class CDNCacheManager: def __init__(self, cache_size_mb: int = 32768): # 32GB default self.cache: Dict[str, Dict] = {} self.access_times: Dict[str, float] = {} self.popularity_scores: Dict[str, float] = {} self.max_size_bytes = cache_size_mb * 1024 * 1024 self.current_size_bytes = 0 def get_cache_key(self, video_id: str, quality: str) -> str: """Generate consistent hash key for video segment""" return hashlib.md5(f"{video_id}:{quality}".encode()).hexdigest()[:16] def calculate_eviction_score(self, key: str) -> float: """LRU + popularity hybrid scoring for cache eviction""" now = time.time() recency = now - self.access_times.get(key, now) popularity = self.popularity_scores.get(key, 0.1) # Lower score = higher eviction priority # Combine recency (seconds) with popularity multiplier return popularity / (1 + recency / 3600) # Normalize by hours def evict_if_needed(self, incoming_size: int): """Evict least valuable content to make space""" while self.current_size_bytes + incoming_size > self.max_size_bytes: if not self.cache: break # Find item with lowest eviction score victim_key = min(self.cache.keys(), key=self.calculate_eviction_score) victim_size = self.cache[victim_key]['size'] del self.cache[victim_key] del self.access_times[victim_key] self.current_size_bytes -= victim_size def cache_video_segment(self, video_id: str, quality: str, data: bytes, popularity: float = 1.0): """Cache video segment with popularity-aware LRU""" key = self.get_cache_key(video_id, quality) segment_size = len(data) self.evict_if_needed(segment_size) self.cache[key] = { 'data': data, 'size': segment_size, 'video_id': video_id, 'quality': quality } self.access_times[key] = time.time() self.popularity_scores[key] = popularity self.current_size_bytes += segment_size def get_video_segment(self, video_id: str, quality: str) -> Optional[bytes]: """Retrieve video segment from cache""" key = self.get_cache_key(video_id, quality) if key in self.cache: self.access_times[key] = time.time() # Update LRU return self.cache[key]['data'] return None

This cache manager implements YouTube's hybrid LRU-popularity algorithm for edge cache management. The eviction scoring combines recency with predicted popularity (from recommendation system) to keep viral content cached longer than standard LRU would allow. The consistent hashing ensures the same video-quality combinations map to the same cache keys across restarts, while the size-aware eviction prevents memory exhaustion during traffic spikes.

Interview Corner — FAANG-Level Questions
  1. Q: How would you design cache invalidation for a global video CDN where content can be updated but you need to minimize cache misses?
    Model Answer: Implement versioned content URLs with push-based invalidation through message queues. Use eventual consistency with vector clocks for ordering, and maintain a grace period where both old and new versions are served during propagation to avoid cache stampedes.
  2. Q: A viral video is causing cache misses and overwhelming your origin servers. How do you handle this traffic spike?
    Model Answer: Implement origin shielding with dedicated shield servers, use consistent hashing to distribute load, enable range request caching for partial content serving, and add circuit breakers with exponential backoff to protect origin during failures.
  3. Q: How would you optimize CDN performance for mobile users with varying network conditions?
    Model Answer: Implement adaptive bitrate streaming with buffer-based quality selection, use HTTP/2 server push for predictable segments, compress metadata with protocol buffers, and maintain separate cache tiers optimized for mobile bitrates with aggressive compression.
